# 多 Agent 协作手册

> 适用范围：English Pet Care Plan 的需求、设计、开发和测试任务
> 维护者：主 Agent / 项目经理
>
> 注意：第 5–6 节记录 v0.2.1 的历史任务卡。自 2026-08-23 起，首轮 Beta 以 `docs/product-requirements.md` v0.3 为准；36/72 小时提醒/休养/重逢不再进入 Beta 实现或验收。

本手册落实 `AGENTS.md` 的多 Agent 规则。目标是让独立工作并行推进，同时确保产品规则、服务端权威边界、测试和最终集成只有一个明确责任人。

## 1. 运行模型

```text
用户目标
  ↓
主 Agent：任务卡、范围和验收
  ├── 产品经理：需求评审 / 原型范围
  ├── UI/UX：页面与状态规格 ──────┐
  └── 后端：模型 / API / 状态机 ───┼─→ 主 Agent 冻结接口
                                     ↓
                               前端：页面与 API 对接
                                     ↓
                               测试：验证、缺陷、回归
                                     ↓
                         主 Agent：整合、全量验证、交付
```

产品、UI/UX 和后端可以在输入稳定后并行；前端必须等待 API 契约和交互状态冻结；测试对完整功能进行独立验证，不直接改业务实现。

## 2. 任务卡模板

主 Agent 在每个功能开始时提供以下信息：

```md
### 任务：<名称>

- 用户价值：
- 范围：
- 非目标：
- 负责人：
- 允许改动路径：
- 输入资料与依赖：
- 安全/数据边界：
- API/状态机冻结点：
- UnitTest / UITest：
- 性能指标：
- 验收标准：
- 验证命令：
```

没有任务卡的需求扩展、依赖升级、跨用户读取、真实收款或外部写入，必须回到主 Agent 评估和获得相应授权。

## 3. 角色使用指南与交付契约

| 交付方   | 最适合介入的场景                                   | 交付物                                                        | 下游使用方               | 完成条件                                           |
| -------- | -------------------------------------------------- | ------------------------------------------------------------- | ------------------------ | -------------------------------------------------- |
| 产品经理 | 问题/机会不清、需要调研、取舍、指标或实验设计时    | 需求评审、优先级、验收、实验指标                              | UI/UX、后端、主 Agent    | 需求、规则、非目标和风险没有未决 P0 歧义           |
| UI/UX    | 需求已冻结、需定义用户流、页面状态或体验/无障碍时  | 页面清单、用户流、加载/空/错/禁用状态、语义选择器、无障碍要求 | 前端、测试               | 每个 P0 流程可按文档验证，不依赖像素坐标或易变文本 |
| 后端     | 涉及事实来源、数据、授权、API、事务、性能或审计时  | OpenAPI、错误码、迁移、鉴权/归属/幂等说明、Pytest 结果        | 前端、测试               | 契约冻结；领域规则由服务端单一裁决                 |
| 前端     | 已有冻结接口和交互规格、需实现跨端页面和端侧状态时 | 页面、请求状态、生成/受控类型、Vitest/Playwright 结果         | 测试、主 Agent           | 不复制积分/状态机；错误与重试可见且可访问          |
| 测试     | 有可验收流程、修复候选或发布/回归风险时            | 缺陷报告、覆盖清单、回归结果                                  | 对应开发 Agent、主 Agent | 每项问题可稳定复现，包含严重级别和证据             |

完整的能力、决策权限与禁止事项以 [AGENTS.md](../AGENTS.md) 第 8.1.1 节为准。主 Agent 应依据本表分配任务，而不是只按文件位置派工。

## 4. 缺陷闭环

1. 测试 Agent 提交 P0/P1/P2 缺陷：环境、前置数据、复现步骤、预期、实际、日志/截图、影响范围。
2. 主 Agent 指定一个责任开发 Agent；非责任人不同时修改相同实现文件。
3. 开发 Agent 补充回归测试、修复并运行受影响检查。
4. 测试 Agent 复测；主 Agent 统一确认关闭并记录已知限制。

## 5. 当前首轮 Beta 的分波方式

| 波次 | 并行角色                 | 目标                                                            |
| ---- | ------------------------ | --------------------------------------------------------------- |
| A    | 产品经理、UI/UX、后端    | 冻结单猫、背词、免费基础互动、提醒/休养/重逢的验收与 API 草案   |
| B    | 前端、后端（仅契约收尾） | 基于冻结契约实现最小闭环                                        |
| C    | 测试、责任开发 Agent     | 验证领养 → 学习 → 基础互动 → 休养后重逢，以及失败和重复提交路径 |
| D    | 主 Agent                 | 全量检查、性能/安全复核、文档整合和交付                         |

当前前端生产依赖存在高风险审计阻塞项。任何 Agent 都不得把“测试通过”解释为可以公开发布；发布仍需要 `npm run audit:prod:release` 达到 critical/high 为零。

## 6. 当前任务卡：首轮 Beta 的状态与界面基础

> 本任务卡已完成并被 v0.3 的“可解释学习—低压陪伴”任务卡取代。历史实现与测试仅保留为探索性资产。

- **用户价值**：让用户先看到“离开不会失去 Momo”的清晰入口，并以可测试、可解释的服务端规则奠定后续学习—陪伴闭环。
- **范围**：服务端实现纯领域的 `normal` / `reminder` / `resting` 状态转换、可注入时钟与幂等结果；前端实现欢迎与安心说明及可注入权威视图模型的只读今日页外壳；UI/UX 交付完整页面状态与语义选择器。
- **非目标**：不接入真实微信登录、数据库、Redis、外部通知、生产密钥或真实支付；不在客户端判定阈值、生成积分或保存宠物状态。
- **责任边界**：后端仅写 `services/api/`；前端仅写 `apps/mini/`；UI/UX 仅写 `docs/ui-ux/`；主 Agent 负责产品基线、接口冻结与集成。
- **安全与数据边界**：所有未来写操作须经服务端身份验证、宠物归属和幂等键校验。当前领域模块不得伪装成已认证生产 API，也不得写入真实数据。
- **状态机冻结点**：领养时间为第一条陪伴事件；`>=36h` 为提醒、`>=72h` 为休养；`feed` / `water` / `tidy` 只在正常或提醒中有效；`reunion` 只在休养中有效并恢复正常；学习不影响恢复资格。
- **UnitTest / UITest**：领域测试覆盖 36/72 小时边界、拒绝路径和同键重试；前端单测覆盖欢迎页、权威视图模型的加载/空/错误/正常展示与语义可访问性。完整端到端闭环待 API 与会话契约冻结后补充。
- **性能指标**：不新增媒体预载、不引入新依赖；欢迎页和只读今日页不引入狗狗、视频、商城或未开放资源。
- **验收标准**：领域结果可被后续数据库/API 层复用且不依赖真实时间；前端不展示伪造的积分/历史，不复制服务端状态机，并能通过受影响的格式、静态检查、类型、单元测试与 H5 构建。
